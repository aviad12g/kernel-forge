# Methodology

## Task Suites

The controlled study uses an internal fused8 suite: `bias_relu`, `sigmoid`, `add_relu`, `residual`, `bias_gelu`, `row_sum`, `layernorm`, and `rmsnorm`. These tasks are small enough for repeated measurement but structured enough to give Triton opportunities beyond isolated elementwise launch overhead. Each task defines a PyTorch reference, deterministic input generation, benchmark shapes, dtype metadata, tolerances, prompt hints, and shape metadata such as feature dimension.

The preserved external artifacts use official KernelBench L1 tasks from `ScalingIntelligence/KernelBench` at commit `423217d9fda91e0c2d67e4a43bf62f96f6d104f1`. The historical run loaded a 100-task pool, ordered it by deterministic family round-robin, and scanned that order until it found 20 feasible tasks. Its 31 recorded memory skips are from that scanned prefix, not the entire loaded pool. The corrected lower-bound estimate accounts for the input-tree copies held by verification, reference and candidate module state, and configured cache-perturbation storage, but not outputs, compiler workspace, all temporaries, or allocator fragmentation. The corrected preflight requests metadata-only tensors; unsupported metadata execution is skipped unless CPU fallback is explicitly enabled. More importantly, the historical adapter violated parameterized task-state and reference-lifecycle contracts. The subset and its outputs are retained for evaluator auditing, not as an external accuracy or performance estimate.

## Candidate Sources

The rigorous fused8 study compares three sources:

- **template**: deterministic Triton templates generated by sweeping conservative block size, warp, stage, shape-specialization, contiguity, and allocation variants;
- **Gemini**: Gemini 3.1 Flash-Lite, with one attempt and three candidates per fused8 task;
- **OpenAI mini**: `gpt-5.4-mini`, with the same fused8 candidate budget.

The historical KernelBench run used Gemini only, with one candidate per selected task and one repair pass over 8 selected failures. These generation artifacts remain useful for prompt, policy, and failure-path auditing, but their correctness and timing rows require corrected CUDA revalidation.

Model identifiers are reported as configured API strings. The fused8 Gemini and KernelBench Gemini configs use `gemini-3.1-flash-lite`; the OpenAI mini fused8 config uses `gpt-5.4-mini`. The local artifact package does not preserve provider response `model` fields for the fused8 runs. KernelBench JSONL records preserve the configured `model` field for each candidate but not a separate provider-returned model-version field.

## Verification

Fused8 candidates expose `forward(*args)`. Every official KernelBench task that defines `Model` requires `ModelNew`, including tasks with an empty `state_dict()`. The adapter materializes `get_init_inputs()` once under fixed seed 0, clones that snapshot into persistent reference and candidate modules, and passes `get_inputs()` to their forward methods. Both modules move to the target device before verification and timing. Free functions are reserved for local synthetic tasks with an explicit `reference_fn` interface. The harness preserves prompt text, raw response, source, policy result, backend metadata, and task metadata.

Verification records shape mismatches, dtype mismatches, runtime exceptions, Triton compile errors, numerical mismatches, timeout/OOM failures, policy failures, and unexpected input mutation. It compares candidate input side effects with the reference, so a candidate may mutate an input only when the reference produces the same final input state. Only candidates that pass correctness verification are benchmarked. Failed candidates remain in the artifact trail and can be included in failure analysis or repair prompts.

### Static Policy Checks

The base policy checker parses candidate source with the Python AST and applies the following implemented checks:

| Check | Detection method | Purpose |
| --- | --- | --- |
| syntax | `ast.parse` | reject unimportable candidates |
| entry point | module `forward` or `ModelNew.forward` lookup | enforce the applicable candidate contract |
| strict imports | allow only Torch allocation/type modules, Triton, math, and typing; reject task/reference imports | reduce fallback and reference access |
| unsafe/import-time calls | reject process, file, dynamic-code, and module-level side-effect calls | prevent obvious import-time abuse |
| suspicious calls | reject reference-like calls and unsupported `self.*` module routing | block direct reference or module fallback |
| Torch compute fallback | inspect the entire selected forward AST for high-level Torch calls, tensor methods, and direct tensor arithmetic | require candidate compute to use Triton when fallback is disabled |
| real Triton launch | require a JIT-decorated local kernel and matching indexed launch | prevent import-only or arbitrary-subscript Triton claims |

These checks are conservative guardrails, not an operating-system sandbox. Passing source is imported and executed in the harness process, so untrusted candidates require disposable process or container isolation and an external timeout.

The template-preservation checker is a separate heuristic path for template-copy runs. It can reject missing `@triton.jit`, missing `BLOCK_SIZE`, changed launch count, try/except wrappers, forbidden torch ops in `forward`, fallback/reference tokens, or a low preservation score.

## Timing Protocol

The rigorous benchmark path uses CUDA events rather than host wall-clock timing [@nvidiaCudaEvents]. The paper-facing protocol is:

| Setting | Value |
| --- | --- |
| timing primitive | CUDA events |
| warmup | 30 iterations |
| measured samples | fused8: 120 per session; historical KernelBench: 100 baseline or 120 candidate/repair |
| repeated sessions | 3 same-process loops |
| cache-state perturbation | enabled, 128 MB CUDA buffer, write mode |
| compiler baseline | `torch.compile max-autotune` [@ansel2024pytorch2] |
| summaries | median, IQR, std, CV, bootstrap CI where available |
| compile/runtime handling | current code materializes compile and records wrapper plus first synchronized call separately from steady-state runtime |

Warmup reduces contamination from lazy initialization and memory-pool setup. CUDA events measure GPU elapsed time directly. Cache-state perturbation is best-effort: the implementation writes a 128 MB CUDA `float32` buffer before measured samples, but it does not guarantee complete L2 eviction. Current code prepares callables before timing, rotates eager/candidate/compile order by session, materializes lazy compilation before runtime sampling, and reports session-level speedup summaries. Historical artifacts used fixed order, pooled sample intervals, and incomplete compile accounting; those fields are not reinterpreted.

A session is a separate benchmark loop inside the same process and same GPU run. Inputs are regenerated with seed `1234 + session_index`, and a fresh timer/cache-flusher object is used. Sessions are not process-independent replicates and do not imply a GPU clock reset.

Because the paper's claim is about measurement stability, tables report repeat medians with uncertainty summaries where available. When the imported artifact summary does not include p25/p75 or bootstrap intervals, the table explicitly marks the uncertainty field as unavailable rather than inferring it.

## Repeatability Labels

OpenKernelForge reports single-run speedups but does not treat them as final evidence. The current implementation uses two related label paths.

Legacy repeatability reports compute repeated `speedup_vs_eager` values, summarize their median and coefficient of variation, and label:

```text
if repeat_median is missing: INSUFFICIENT_DATA
elif repeat_median >= 1.0 and coefficient_of_variation <= 0.10: REPEAT_STABLE_WIN
elif original_speedup >= 1.0 and repeat_median < 1.0: SINGLE_RUN_ONLY_WIN
elif repeat_median >= 1.0: UNSTABLE
else: BELOW_EAGER
```

The rigorous benchmarker computes per-session speedups and sets:

```text
stable_above_eager =
    median(session_speedups) >= 1.0
    and all(session_speedup >= 0.98 for session_speedup in session_speedups)
```

KernelBench candidate labels then use:

```text
if speedup_vs_eager is missing: INSUFFICIENT_DATA or BENCHMARK_FAILED
elif speedup_vs_eager >= 1.0 and stable_above_eager: REPEAT_STABLE_WIN
elif speedup_vs_eager >= 1.0: UNSTABLE
else: BELOW_EAGER
```

CI/IQR fields are reported when preserved, but the current labeler does not use CI/IQR thresholds.

Imported fused8 summaries use the legacy repeatability-report labels because those runs predate local preservation of current session-label inputs. Historical KernelBench records contain rigorous-label fields, but those labels are provisional because the surrounding adapter and baseline lifecycle were invalid. The current rigorous labeler is preferred because it records session-level parity directly.

The thresholds are implementation defaults, not tuned values. The legacy `CV <= 0.10` rule is inherited from older repeatability reports. The rigorous `tau = 0.98` default allows small session-level timing variation while still requiring an above-eager median. Existing artifacts do not preserve the per-session speedup vectors needed to recompute headline labels under alternative `tau` values, so the paper does not claim threshold robustness.

The labels are:

- `REPEAT_STABLE_WIN`: repeat median remains above eager without contradictory sessions;
- `SINGLE_RUN_ONLY_WIN`: the legacy path has a distinct original win that falls below eager by repeat median;
- `BELOW_EAGER`: the candidate is correct but slower than eager;
- `UNSTABLE`: measurements are too inconsistent for a stable claim;
- `INSUFFICIENT_DATA`: the run lacks enough timing evidence.

These labels are the main methodological unit of the paper. They separate correctness, search signals, and stable performance claims.

## Environment

The historical KernelBench artifacts record Python 3.12.3, Linux 6.8.0-87-generic, Torch 2.8.0+cu128, Triton 3.4.0, CUDA available, one NVIDIA GeForce RTX 5090, and a passing tiny Triton kernel. The fused8 campaign was reported on the same RTX 5090/Torch/Triton RunPod stack, but its full environment probes are not present in this local package.

GPU and memory clocks, power limit, persistence mode, ECC status, and thermals were not recorded as locked or controlled. This is a limitation of the current artifact package.
