# Historical KernelBench Repairability Criterion

The repair subset was generated by `scripts/analyze_kernelbench_candidate_failures.py` from the affected historical Gemini run. This document records the selection heuristic for auditability. The obsolete free-function state contract and reference lifecycle prevent interpreting the repair outcomes as evidence of repair effectiveness.

## Failure Categories

The analyzer assigns one failure category per failed candidate using extraction status, policy result, verification cases, error text, and traceback summaries.

Implemented categories include:

- `syntax/import error`;
- `wrong function signature`;
- `wrong number of inputs`;
- `shape mismatch`;
- `numerical mismatch`;
- `illegal torch fallback`;
- `Triton compile error`;
- `runtime exception`;
- `timeout/OOM`;
- `verification harness issue`;
- `other`.

The affected evaluator recorded 17 failed candidates:

| Category | Count |
| --- | ---: |
| numerical mismatch | 9 |
| timeout/OOM | 4 |
| runtime exception | 2 |
| Triton compile error | 2 |

## Repairability Labels

The repairability label is heuristic and candidate-specific.

| Repairability | Implemented criterion |
| --- | --- |
| high | wrong signature, wrong input count, shape mismatch, Triton compile error, or numerical mismatch in matmul/loss tasks |
| medium | runtime exception or other categories not explicitly high/low |
| low | numerical mismatch in convolution, timeout/OOM, verification harness issue, unsupported pattern, runtime exception involving invalid `forward.` state, or convolution tasks where hidden model parameters are likely unavailable |

## Repair Subset Selection

The script selects up to `max_repair = 8` tasks by scoring failed candidates:

- high repairability: `+100`;
- medium repairability: `+50`;
- numerical mismatch: `+25`;
- Triton compile error: `+20`;
- matmul/loss family: `+15`;
- pooling family: `+5`;
- convolution family: `-75`;
- timeout/OOM or verification harness issue: `-100`.

Candidates are excluded if:

- repairability is low;
- failure category is `timeout/OOM`;
- failure category is `verification harness issue`;
- op family is convolution.

The remaining candidates are sorted by score and task id, then the top eight are selected.

## Selected Repair Tasks

The selected repair tasks were:

- `KernelBench__level1__10_3D_tensor_matrix_multiplication`;
- `KernelBench__level1__13_Matmul_for_symmetric_matrices`;
- `KernelBench__level1__14_Matmul_for_upper_triangular_matrices`;
- `KernelBench__level1__15_Matmul_for_lower_triangular_matrices`;
- `KernelBench__level1__16_Matmul_with_transposed_A`;
- `KernelBench__level1__98_KLDivLoss`;
- `KernelBench__level1__11_4D_tensor_matrix_multiplication`;
- `KernelBench__level1__44_Average_Pooling_1D`.

`KLDivLoss` was selected because it was a loss-family numerical mismatch, classified high repairability, and its suggested instruction was to match PyTorch reduction semantics, log/probability convention, and numerical stabilization. The affected evaluator later recorded it as verified and repeat-stable; that observation remains historical audit metadata pending corrected revalidation.

This repairability rule is not a learned predictor. It is a transparent heuristic used to cap a single repair iteration.
